# Orbit CRM versioning

Orbit CRM uses semantic Git tags and GitHub Releases as the authoritative version record. Versions are never calculated from the number of commits and are not manually stored in application source files.

```text
v1.0.0
v1.0.1
v1.1.0
```

## Conventional Commits and automatic releases

Every pull request into `main` must have a [Conventional Commits](https://www.conventionalcommits.org/) title. The `Validate Conventional Commits` workflow checks that title.

After a qualifying commit reaches `main`, `Automatic Semantic Tagging` creates a semantic tag, builds the tagged site, and creates a GitHub Release only if the build succeeds. Existing tags are never rewritten.

| Commit intent | Release effect |
| --- | --- |
| `fix:` | Patch increment, such as `v1.0.1` |
| `feat:` | Minor increment, such as `v1.1.0` |
| `!` or `BREAKING CHANGE:` | Major increment, such as `v2.0.0` |
| `docs:`, `chore:`, `test:`, `ci:` | No release by itself |

Allowed conventional types are `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, and `revert`. A scope is optional. Use a short imperative summary without a trailing period.

## Validation

The release workflow validates `vMAJOR.MINOR.PATCH` tags and runs `npm ci` plus `npm run build` from `site/` against the tagged source before publishing a GitHub Release.

Tags pushed manually are checked by `Validate manually pushed release tag`. Tags generated by GitHub Actions are validated within `Automatic Semantic Tagging`, which avoids relying on an additional workflow trigger that GitHub does not guarantee for events created with its default token.

## Repository configuration

Protect `main` with a branch ruleset that requires pull requests and the `Validate PR title` status check. Use squash merges so the pull request title becomes the commit message that determines the semantic release.
